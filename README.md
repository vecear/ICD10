# ICD-10 門診導引

單一離線 HTML 的 ICD-10-CM 選碼工具，為看診當下設計：內科門診／內科急診／外科三種模式、
依身體部位的症狀導向面板（每個部位最上面掛該部位的常用碼）、相關碼連鎖推薦、
就診清單一鍵貼入 HIS、
全庫即時搜尋，以及 DM／HTN／LIPID 的**健保規範條文**（給付規定與臨床治療目標，
每條標出處與查證日期，並附健保署官方條文 PDF）。
工具本體是 [`dist/icd10.html`](dist/icd10.html) 一個檔案（約 2.2 MB），
免安裝、免網路、零外部請求。官方條文 PDF 另外放在
[`健保條文/`](健保條文/)，要與 `icd10.html` 放在同一層（打包腳本會一起帶走）。

## 三種版面

| 版面 | 用途 |
| --- | --- |
| **桌機工作台**（預設） | 全螢幕三欄：左部位、中面板、右就診清單＋HIS 預覽。看診主力版面。 |
| **側掛窄欄** | 壓成一條窄欄貼在螢幕邊，讓 HIS 佔滿其餘空間；可用 Document Picture-in-Picture 把整條窄欄丟進永遠置頂的小視窗，浮在 HIS 上面。在主視窗時限寬 600px 並靠右貼齊（見下）。 |
| **手機** | 整列式觸控介面（每列 48px）、底部固定清單列與可展開抽屜。 |

工作台的**常見疾病不收合、全部列出來**（2026-09-01 使用者要求）：1440px 橫向放得完，
而每點一次展開就是一次中斷。**側掛窄欄與手機仍然收合**——176px 底下把每個面板的
二十幾個常見疾病全攤開，捲軸會長到不能用（見 [`docs/dense-ui-principle.md`](docs/dense-ui-principle.md)）。

常用碼掛在部位底下、跟著部位鈕走，而且直接展開：「常用慢性病」在「常用」，
「病原體附加碼／抗藥性」與「常見感染」依序在「全身／感染」——不是「感染科追蹤」，
那一格是 HIV／結核／OPAT 的長期追蹤，跟臨時要編一個感染碼是兩件事。
急診與外科的快選沒有對應的部位分類，仍然掛在面板上方、維持收合。

桌機兩種版面各有一顆直接鈕，選擇會記住：

- 工作台 header 最右的**「側掛置頂」**——一次做完「切成側掛窄欄」與「開置頂小視窗」。
  ≤1239px 時收成圖示（名稱在 `aria-label` 與 `title`），免得把搜尋框壓沒。
- 側掛窄欄 header 的**「展開」**——回到工作台，置頂小視窗會一併關閉。它就在窄欄自己的
  header 上，所以整條窄欄被搬進置頂小視窗時仍然按得到（那是該狀態下唯一的回頭路）。

窄欄旁邊的「置頂」鈕維持獨立：可以只開關小視窗而不換版面，也保留「窄欄但不置頂」
這個狀態——診間用 AHK 的 Ctrl+Alt+D 貼齊時走的就是它（見 `tools/README.md`）。
置頂開不起來時（不支援／被瀏覽器擋下）版面照樣切過去，只是多一則說明。

**側掛窄欄在主視窗時限寬、靠右貼齊。** 網頁改不了主瀏覽器視窗的大小
（`resizeTo` 對一般分頁無效），所以解除置頂、側欄回到最大化的視窗時，沒有上限就會
攤成一片全寬版面——那既不是窄欄也不是工作台。

寬度是**解除置頂那一刻小視窗的寬度**（`render-dock.js` 量了寫進 `--dock-w`）：
要的是「維持側掛的寬度，只是沒強制置頂」。沒置頂過就用預設 340px，那也是
Ctrl+Alt+D 貼齊的寬度。置頂小視窗**不**套這個上限——那個視窗的尺寸是自己拉的，
內容該填滿它。

**解除置頂時，主視窗若寬到足以跑工作台（≥ 900px）就直接切回工作台。** 因為網頁
改不了自己所在視窗的大小——實測：一般分頁呼叫 `resizeTo(340,900)` 後 `innerWidth`
1266 → 1266 完全沒動，同一行在 `window.open` 開出來的視窗上則是 1266 → 326。
所以「側欄回到一個最大化的視窗」只能是「一條窄欄＋一大片空白」，那既不是側掛
也不是工作台。視窗本來就窄（Ctrl+Alt+D 貼齊的 340px）則維持側掛。

視窗寬度未達 900px 時會自動改用手機版面（此時設定面板會說明目前生效的是哪一種、
以及放寬視窗就會回去），因此在筆電上把視窗縮成半螢幕也不會變成擠爆的桌機版。

## 使用

用 Edge / Chrome 開啟 [`dist/icd10.html`](dist/icd10.html)。

- **搜尋**：中文（蜂窩）、英文（cellulitis）、代碼前綴（L03 或 E119）皆可；按 Enter 直接加入第一筆。
- **內科導引**：先選內科門診或內科急診，再依身體部位挑主訴、常見相關疾病與評估碼。
- **急診提醒**：「優先排除／提醒評估」僅供醫師複核，不是自動診斷或急診分流；推薦碼需逐一點選才會加入清單。
- **外科導引**：外傷、傷口、膿瘍、疝氣與術後追蹤等常見情境。
- **點任何代碼**加入就診清單，同時跳出相關代碼（臨床關聯＋同類目）供連鎖加選。
- 灰色虛線代碼為類目碼（不可申報），點了不會加入清單。

### 健保規範條文（DM／HTN／LIPID）

一顆 **健保規範條文** 鈕叫出浮層，浮層最上方是 DM／HTN／LIPID 三個分頁，
點哪個看哪個；下次再開會停在上次看的主題。內容是該慢性病的**健保給付規定**與
**臨床治療目標**，給不常看慢性病的醫師在看診當下瞄一眼用。
關閉用關閉鈕、`Esc`，桌機另可點面板以外任一處。

入口原本是 DM／HTN／LIPID 三顆並排，2026-09-01 收成一顆——同一排現在還要放
**血脂計算機**與 **CCr**（後者從 header 搬下來），176px 的窄欄放不下五顆。
主題選擇沒有消失，只是往後挪一步：浮層是 modal，開著時外面的鈕被遮罩蓋住，
本來就只能靠面板內那排分頁換主題。
位置依版面而異：桌機工作台常駐在 header，側掛窄欄與手機放在捲動內容區的最上面
（兩者的固定版面寸土寸金，見 [`docs/dense-ui-principle.md`](docs/dense-ui-principle.md)）。

**每個主題最上方是官方條文 PDF 連結**，指向 [`健保條文/`](健保條文/) 底下的檔案
（藥品給付規定的通則、第二節、第五節，加 PCSK9 事前審查申請表）。放在速判摘要之前是刻意的：
整理過的速查沒有機器可驗的權威來源，能反駁它的只有原始條文，所以原始條文要是第一眼
看得到的東西。`href` 由主文件的 `baseURI` 算成絕對路徑——側掛置頂時整棵窄欄在
Document PiP 的 `about:blank` 文件裡，相對路徑會解析到那邊去。
`chronic_care.json` 的 `docs[].file` 對不上實際檔案時**建置直接失敗**：
那種錯的表現是醫師在診間點下去說找不到檔案，而診間補不了檔。

**這一塊與代碼區塊有一個本質差異，使用時務必記得**：診斷碼可以逐碼比對健保署官方全庫、
錯了建置就失敗；**給付規定沒有任何機器可驗的權威來源**。所以：

- 每一條都把**出處**與**查證日期**直接印在畫面上（不是藏在提示或註腳裡）。
- 帶生效日的條文會依**當天日期**自動只顯示現行版本；已公告但還沒生效的會另外標
  「新版將於 X 日生效」，不會提前套用、也不會藏起來。
- 免責在「設定 → 關於」那一句（三套版面都叫得出來）。面板內原本也有一句，2026-08-26 移除：
  每天開面板的人只有第一次會讀它，在 176px 窄欄裡它擋掉的閱讀空間比提醒價值大。
- 條文依臨床決策順序分組：**能不能開 → 怎麼開 → 別踩雷 → 不給付 → 治療目標**
  （看到異常數值時的實際查閱順序：先看有沒有給付，再看怎麼開，最後才是目標）。
- 條文下方的「補充說明」收合著，點開是例外、依據與容易誤讀的地方。**數字看起來衝突時先點開它**
  ——例如糖尿病指引的血壓目標 <140/90 與高血壓指引的 <130/80 兩者都對，差在量測基準
  （後者是 722 法則的居家血壓）。
- 條文與補充都**一條一行**：依句號與分號斷段（括號內的分號不切），掛項目符號並懸掛縮排，
  換行的續行才不會跟「下一條」長得一樣。行首的短標（「起始門檻：」「篩檢：」）另外標重，
  因為那正是掃視時要找的詞。斷段只切不改字——`splitSentences` 的段落接回去必須逐字等於
  資料檔原文，E2E 直接拿 `textContent` 比對 `chronic_care.json`。
- **主文的短標會提成獨立的抬頭行**，底下所有條件平行掛（`fillSegments` 的 `promoteLead`）。
  多數給付規定的原文是一張**表**，抬頭是表名、每個分號段是一列；把抬頭黏在第一列上等於
  宣告它只管第一條。所以維護 `text` 時請照這個形狀寫：**`抬頭：條件一；條件二`**，
  條件本身若有決策鍵（如 TG 區間）就再寫成 `TG 200–499：須…`，它會被當次級短標標重。
  **補充（`detail`）刻意不提抬頭**——它是散文，同一段裡有好幾個短標（「眼底：…。腎功能：…」），
  提第一個會把後面不相干的段落錯掛到它底下。

### 血脂計算機（給付試算）

「健保規範條文」右邊的 **血脂計算機** 鈕（標籤寫全名，免得被當成血脂的條文）。
輸入血脂值與勾選病史，
算出 ASCVD 風險分級、表一的起始門檻與本例達不達標，並附上表二品項的例外門檻。

**為什麼需要它**：LIPID 的給付判定有三個機械步驟特別容易錯，而三個都不需要臨床判斷——
用錯表（表一是主表，表二只適用公告明列「不適用表一」的健保代碼）、極高／非常高風險的
「組合」條件接錯（是「冠狀動脈疾病**合併**什麼」，不是單一條件）、兩張表的風險因子定義混用
（表一 6 項含代謝症候群、HDL-C 女性 < 50；表二 5 項含「或停經者」、HDL-C 男女同為 < 40）。

**兩張表一律都算**。表一是主表，表二在面板上退為次要區塊——但沒有移除，因為公告明列
「不適用表一」的那批代碼含 atorvastatin、rosuvastatin，常到不能不算。

**風險分級寫成一個由高往低的階梯**（LIPID 分頁，速判摘要下方）：六級各自寫出判準、
那一級的 LDL-C 數字（門檻＝目標）與能不能直接開藥，底下另列中／低／0 項要數的 6 項風險因子。
判準逐條照官方「ASCVD 風險等級定義」寫，數字則與 `src/logic.js` 的 `LIPID_ONE`
逐項比對（`tests/test_chronic_care.py::test_risk_ladder_matches_the_thresholds_in_logic_js`）
——這一頁與計算機是同一套判定的兩個出口，講的若不是同一套數字，比兩邊都沒有還糟。

**表一用的是哪些藥**（階梯下方）：條文的「處方規定」欄只寫類別（statin、ezetimibe、
PCSK9 單株抗體、siRNA、ATP citrate lyase 抑制劑），這裡把台灣實際有的學名對進去，
並把**健保給付狀態與學名並排**——表一把 siRNA 與 ATP citrate lyase 抑制劑列為未達標時
可考慮的 non-statin 選項，但健保沒有收載（2.6 全文檢索命中 0），只列學名等於引導醫師
開一個病人要自費的藥。`covered` 少了或給付狀態沒寫，`build.py` 會讓建置失敗。
fenofibrate 與 gemfibrozil 刻意不收：它們走降三酸甘油酯那張表，混進來會讓人拿表一的
LDL-C 門檻去開 fibrate。

**「不適用表一」的成分完整列在兩個地方**：LIPID 條文分頁（速判摘要下方）與血脂計算機的
表二區塊，兩邊同源於 `chronic_care.json` 的 `topics[lipid].tableTwoOnly`，不各存一份。
內容是 9 種成分共 116 個健保代碼（simvastatin 19、lovastatin 3、pravastatin 12、
fluvastatin 3、atorvastatin 35、rosuvastatin 25、pitavastatin 14、
pravastatin ＋ fenofibrate 複方 1、atorvastatin ＋ amlodipine 複方 4），
清單逐列讀自健保署官方第二節 `.docx` 的 2.6.1 對照表，再與同一份 PDF 交叉比對。
**刻意只收到成分層級**：116 列的代碼與品名變動頻繁，嵌進單檔就是製造一個會過期又看起來
權威的東西；成分層級足以回答「我開的這個要對哪張表」。`codeCount` 與各成分加總對不上時
`build.py` 會讓建置失敗——畫面上那句「限『不適用表一』的 N 個健保代碼」不能跟底下的清單自相矛盾。
同一位病人可能表一未達、表二卻符合（或反之），差別只在你要開的品項走哪一張表——
結論不同時面板會明講。判定邏輯是 `logic.js` 的純函式 `lipidCoverage()`，
單元測試在 `tests/logic.test.mjs`（逐級門檻、極高風險的組合條件、兩表風險因子定義的三處差異、
表二的「LDL 或 TC 兩選一」、fibrate 的兩列、以及沒填數值時不下判斷）。

**結果區與剪貼簿都照臨床思考流程排**（2026-09-01）：
「哪一級、憑什麼 → 能不能直接開藥 → 門檻與目標 → 結論」。
原本是「分級 → 門檻 → 結論 → 依據」，依據落在結論之後，等於要求先接受一個判定再回頭找理由。

**「複製結果」輸出的是病歷文字，不是計算機報表**：帶標籤的短行（分級／處方／門檻／目標／
註記／檢附），條文寫全名（「全民健康保險降膽固醇藥物給付規定表一」）、附出處與版本。
刻意不出現「試算／計算機」字樣——讀病歷的是審查醫師，寫工具名只會引出多餘的問題。
目的是被核刪時證明「當時就符合」。範例：

**兩張表都寫**（2026-09-01）。原本只寫符合的那一條（2026-08-27 的要求），改的理由更強：
同一位病人在兩張表可能結論不同，而走哪一張只看所開品項的健保代碼；病歷只寫一張，
等於把「換個代碼就不符合」這件事藏起來，而那正是會被核刪的地方。

```
【降血脂給付依據】58 歲男性，LDL-C 95、TC 180 mg/dL

降膽固醇藥物：依「全民健康保險降膽固醇藥物給付規定表一」
　分級　高風險（糖尿病）
　處方　可與藥物治療並行（生活型態改變同時進行，當天就能開藥）
　門檻　LDL-C ≧ 100 → 本例 95 mg/dL，未達
　目標　LDL-C < 100；次要 non-HDL-C < 130

降膽固醇藥物：依「全民健康保險降膽固醇藥物給付規定表二」（限公告明列「不適用表一」之健保代碼）
　分級　心血管疾病或糖尿病（糖尿病）
　處方　可與藥物治療並行（生活型態改變同時進行，當天就能開藥）
　門檻　LDL-C ≧ 100 或 TC ≧ 160 → 本例 LDL-C 95、TC 180 mg/dL，已達
　目標　LDL-C < 100 或 TC < 160
　註記　兩表結論不同：本例符合「…表二」、不符合「…表一」，請依所開品項之健保代碼適用之表別認定

（依藥品給付規定第二節 2.6.1，115.8.21 版）
```

### 品項反查（代碼／商品名／學名 → 表一或表二）

計算機最底下的「查品項」欄位。輸入健保代碼、商品名（中英文）或學名，回答
**「我開的這個走表一還是表二」**——這是整份速查裡最會被憑印象猜錯的一件事：
同一個 CRESTOR 20MG，`B024129100` 走表一（極高風險門檻 55）、`BC24129100` 走表二（門檻 100），
同一位病人一個符合一個不符合。

三種情境（使用者 2026-09-01 指定）：沒有病人資料時只回表別；有病人資料時每一筆帶
「本例符合／不符合」；沒打字時反過來列符合的那張表底下有哪些學名可用。
**刻意不合併成單一結論**：兩張表可能一符合一不符合，硬湊成「可不可以開」
會把「換個代碼就不符合」藏起來。

**不能假設「大多數走表一」**：就現行給付中的品項而言表二反而較多（116 vs 49），
逐學名看每一種 statin 都是表二多於表一。這一條是實際寫錯過的判斷——
把已停付的死碼算進去會得到「表一 255／表二 116」的相反印象，
而錯的方向會讓醫師少對代碼。`tests/test_lipid_products.py` 把它釘住了。

資料在 [`src/curated/lipid_products.json`](src/curated/lipid_products.json)（約 130 KB，
611 個代碼，其中**現行給付中 241 個**：表二 116、表一 49、其他章節 76；另 370 個支付價 0
＝已停止給付，留著但標記，因為醫師打了那個代碼要看到「已停付」而不是「查無」）。由
[`build/fetch_lipid_products.py`](build/fetch_lipid_products.py) 從兩個官方來源產生：
健保署「健保用藥品項查詢項目檔」（開放資料，**每月更新**）＋2.6.1 的「不適用表一」對照表。
`build.py` 的 `check_lipid_products()` 檢結構（代碼樣式、重複、表別值），
並在 `checked` 超過 3 個月時警告——這份比慢病速查更會過期，門檻設得比它短。

搜尋與判定是 `logic.js` 的純函式（`lipidFindProducts`／`lipidSummarize`／`lipidProductVerdict`），
單元測試在 `tests/logic.test.mjs`，資料契約在 `tests/test_lipid_products.py`。

**兩張表的判定下方都列出現行給付中的品項（商品名＋劑量）**（2026-09-01 使用者要求
「表一就請寫有給付的品項，表二請寫詳細的商品名跟劑量」）。依學名分組，
品名縮寫只拿掉劑型字樣——`XL`、`OD` 與引號裡的廠標一個都不能掉，那些是同名不同品項的關鍵
（`Tulip"SDZ"` 走表一、`Tulip` 走表二；`Lescol XL 80mg` 與 `Lescol 40mg` 是兩回事）。
完整官方品名與健保代碼放在 `title`，要跟 HIS 對字時用。已停付的品項不列。

**預設收合，點學名才展開**（原生 `<details>`／`<summary>`，不經 interactions.js 的委派，
所以置頂時不會失效）。開合狀態記在模組層的 Set 並在重建時還原——結果區每打一個數字
就整個重繪，不記就會「展開之後改一個數值又縮回去」，等於這個功能沒做。

**條文分頁把品項列在藥理類別裡面**（2026-09-01「健保規範條文分頁也要改」，
使用者選了「類別裡直接列品項，並拿掉下面兩份清單」）：同一頁把 165 個品項列兩次是純粹的損耗。
類別展開後是「學名 → 該學名的品項（帶表別）」，學名那一行保留條文的劑量錨點
（「高強度例：40 mg 以上」——品項檔沒有這個資訊）。開合狀態與計算機共用。
類別區塊本身可收合，但**給付標籤留在收合的那一行**：
「自費」藏起來等於引導醫師開一個病人要付錢的藥。

品項檔的**主成分欄對複方會騙人**（Caduet 記 AMLODIPINE、2.6.3 的 ezetimibe 複方記 statin），
照學名分組會在 statin 類底下印出一行「amlodipine」。所以 `match` 可以帶 `labels`
（學名→標籤）與 `bySection`（章節→標籤）把分組名蓋掉。

**類別層級的資訊留在條文分頁**（`chronic_care.json` 的 `topics[lipid].drugs`）：
那一頁回答「表一叫我開什麼類別的藥」，計算機回答「我實際能開哪一個品項」。
給付狀態與學名並排是刻意的：siRNA 與 ATP citrate lyase 抑制劑被表一點名，
但健保沒收載，只列學名等於引導醫師去開一個病人要自費的藥；
計算機那邊用一行帶過（PCSK9 走 2.6.4 須事前審查、那兩類自費）。

### CCr 計算機（Cockcroft-Gault）

**血脂計算機**右邊的 **CCr** 鈕叫出肌酸酐廓清率計算機，供抗生素劑量調整用。
（2026-09-01 從 header 的「日期」右邊搬過來：兩個計算機都是「輸入數值換一個判斷」，
放一起只要記一個位置。**它沒有讓 1c 的 header 變矮**——量到的數字與代價見
[`docs/dense-ui-principle.md`](docs/dense-ui-principle.md)。）
輸入性別、年齡、體重（kg）、肌酸酐（mg/dL），身高（cm）選填。

`CrCl = (140 − 年齡) × 體重 × (女性 ×0.85) / (72 × Cr)`

**體重用哪一個由 BMI 決定**（依 [MDCalc](https://www.mdcalc.com/calc/43/creatinine-clearance-cockcroft-gault-equation)
採用的 Brown et al／Winter et al）：BMI <18.5 用實際體重、18.5–24.9 用理想體重（Devine）、
≥25 用調整體重（理想 + 0.4×(實際 − 理想)）。這一步是劑量最容易錯的地方——同一位病人
用不同體重算可以差到將近兩倍，所以畫面**一律標明主值是用什麼體重算的**，並把實際／理想／
調整三種結果並列；主值只是依 BMI 的一般建議，肌肉量少、截肢、腎功能不穩者仍需醫師自己挑。
沒填身高就只能用實際體重，面板會直說。

計算邏輯是 `logic.js` 的純函式 `creatinineClearance()`，單元測試在 `tests/logic.test.mjs`
（公式、Devine、BMI 分支、調整體重係數、無效輸入一律不回 NaN）。

**免責**：Cockcroft-Gault 估計值，僅適用腎功能穩定者；可能高估 GFR 10–20%，
體重極端時更不準。實際劑量請依藥品仿單與臨床判斷。

### 維護慢病速查的內容

資料在 [`src/curated/chronic_care.json`](src/curated/chronic_care.json)，檔頭的 `_schema`
就是欄位說明（建置時會剝掉，不進 dist）。結構是 `topics[]`（`dm`／`htn`／`lipid`）→
`sections[]`（`kind`：`target` 臨床治療目標／`coverage` 健保給付規定／`caution` 實務提醒）
→ `items[]`。每條 item：

| 欄位 | 意義 |
| --- | --- |
| `text` | 一行講完的重點，畫面上直接顯示 |
| `detail` | 展開後的補充（例外、依據、容易誤讀之處），可省略 |
| `source` | 出處名稱＋條號＋版本日期。**不可放網址**——`assert_offline()` 會讓建置失敗 |
| `checked` | 本條的查證日期（`YYYY-MM-DD`）。超過 **6 個月**建置時會印醒目警告 |
| `effectiveFrom` / `effectiveTo` | 適用區間，**兩端都含當日**，可省略（省略＝該端無限） |

**改版怎麼寫**：健保署公告換版時，**不要直接改掉舊條文**——給舊版補上
`effectiveTo`（舊制最後一天），新版另開一條帶 `effectiveFrom`（生效日）。這樣公告日到生效日
之間，醫師看到的是現行的舊制＋一則「新版將於 X 日生效」的預告；生效當天自動翻版，
不需要任何人在那天去改檔案。生效日過後可以擇期把過期條文刪掉（它已經不會顯示）。

**定期重查**：`python build/build.py` 會掃所有 `checked` 日期，超過 6 個月
（`build/build.py` 的 `CHRONIC_CHECK_MAX_MONTHS`）就印出逐條警告與門檻日期。
**警告不會讓建置失敗**——過期的規定會誤導醫師，但讓建置失敗等於門診當天沒工具可用，那更糟。
重查健保署當期公告後，更新該條的 `checked`（內容沒變也要更新：那個日期的意思是
「有人在這天確認過」，不是「這天改過」）。

三個主題的 key 在 `src/state.js` 的 `CHRONIC_TOPICS` 另有一份鏡像（狀態層是零 DOM 的純模組，
讀不到資料檔）。兩邊分歧時建置會警告，`tests/test_chronic_care.py` 也會擋。

## 免責

**選碼部分**：本工具僅輔助選碼，不構成醫療或申報建議；最終診斷碼以醫師判斷與健保署現行規範為準。
它不做診斷，也不判斷該做什麼——只把醫師已經做好的決定轉換成代碼。

**慢病速查部分**：加入 DM／HTN／LIPID 速查之後，本工具已跨進**臨床參考**的範疇——它會顯示
治療目標數值與健保給付門檻。這一塊必須另外說清楚：

- **不是給付判定**。給付規定逐年修訂、且有品項層級（健保代碼／廠牌）的例外，那一層刻意不收進來。
  能不能申報，一律以**健保署當期公告**為準；有疑義請直接查當期公告或向健保署確認。
- **不是治療處方**。治療目標出自國內外現行指引的一般建議，實際目標必須依個別病人的年齡、共病、
  低血糖風險、預期餘命與偏好調整；指引本身對部分族群刻意不給單一數字。
- **可能過期**。每條都標了出處與查證日期，請看那個日期再決定要不要採信；超過半年未重查的內容，
  建置時會警告維護者，但**已經散出去的 HTML 檔不會自己更新**。
- 使用本工具產生的任何臨床或申報決定，責任仍在使用者。

**CCr 計算機部分**：它算出來的數字會直接影響抗生素劑量，風險與慢病速查同級：

- **公式本身就有誤差**。Cockcroft-Gault 可能高估 GFR 10–20%，在體重極端（過輕、特別是
  肥胖）時更不準，且**只適用腎功能穩定者**——急性腎損傷、透析中、腎功能正在變動的病人不適用。
- **「用哪個體重」是判斷不是計算**。畫面依 BMI 給的主值只是一般建議；肌肉量少、截肢、
  長期臥床、水腫的病人都可能要改用別的體重，所以三種結果一律並列讓醫師自己挑。
- **不是劑量建議**。本工具不查任何藥品的腎功能劑量表；實際劑量請依藥品仿單與臨床判斷。
