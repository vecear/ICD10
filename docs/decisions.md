# 設計決策紀錄

這裡收的是從 README 搬出來的「為什麼」：帶日期的使用者要求、實測證據、設計取捨，依日期排序；沒有日期的放在最後的「未標日期」節。README 只留結論，理由來這裡查。

## 2026-08-26 移除面板內免責提示

- 免責在「設定 → 關於」那一句（三套版面都叫得出來）。面板內原本也有一句，2026-08-26 移除：
  每天開面板的人只有第一次會讀它，在 176px 窄欄裡它擋掉的閱讀空間比提醒價值大。

（出自 README 的『健保規範條文（DM／HTN／LIPID）』節）

## 2026-09-01 工作台常見疾病展開不收合

工作台的**常見疾病不收合、全部列出來**（2026-09-01 使用者要求）：1440px 橫向放得完，
而每點一次展開就是一次中斷。**側掛窄欄與手機仍然收合**——176px 底下把每個面板的
二十幾個常見疾病全攤開，捲軸會長到不能用（見 [`docs/dense-ui-principle.md`](dense-ui-principle.md)）。

（出自 README 的『三種版面』節）

## 2026-09-01 健保規範條文入口三顆併成一顆

入口原本是 DM／HTN／LIPID 三顆並排，2026-09-01 收成一顆——同一排現在還要放
**血脂計算機**與 **CCr**（後者從 header 搬下來），176px 的窄欄放不下五顆。
主題選擇沒有消失，只是往後挪一步：浮層是 modal，開著時外面的鈕被遮罩蓋住，
本來就只能靠面板內那排分頁換主題。
位置依版面而異：桌機工作台常駐在 header，側掛窄欄與手機放在捲動內容區的最上面
（兩者的固定版面寸土寸金，見 [`docs/dense-ui-principle.md`](dense-ui-principle.md)）。

（出自 README 的『健保規範條文（DM／HTN／LIPID）』節）

## 2026-09-01 結果排序改依臨床思考流程

**結果區與剪貼簿都照臨床思考流程排**（2026-09-01）：
「哪一級、憑什麼 → 能不能直接開藥 → 門檻與目標 → 結論」。
原本是「分級 → 門檻 → 結論 → 依據」，依據落在結論之後，等於要求先接受一個判定再回頭找理由。

（出自 README 的『血脂計算機（給付試算）』節）

## 2026-09-01 兩張表的結果都寫進病歷

**兩張表都寫**（2026-09-01）。原本只寫符合的那一條（2026-08-27 的要求），改的理由更強：
同一位病人在兩張表可能結論不同，而走哪一張只看所開品項的健保代碼；病歷只寫一張，
等於把「換個代碼就不符合」這件事藏起來，而那正是會被核刪的地方。

（出自 README 的『血脂計算機（給付試算）』節）

## 2026-09-01 品項反查的三種情境

三種情境（使用者 2026-09-01 指定）：沒有病人資料時只回表別；有病人資料時每一筆帶
「本例符合／不符合」；沒打字時反過來列符合的那張表底下有哪些學名可用。
**刻意不合併成單一結論**：兩張表可能一符合一不符合，硬湊成「可不可以開」
會把「換個代碼就不符合」藏起來。

（出自 README 的『品項反查（代碼／商品名／學名 → 表一或表二）』節）

## 2026-09-01 兩張表下方列出品項與劑量

**兩張表的判定下方都列出現行給付中的品項（商品名＋劑量）**（2026-09-01 使用者要求
「表一就請寫有給付的品項，表二請寫詳細的商品名跟劑量」）。依學名分組，
品名縮寫只拿掉劑型字樣——`XL`、`OD` 與引號裡的廠標一個都不能掉，那些是同名不同品項的關鍵
（`Tulip"SDZ"` 走表一、`Tulip` 走表二；`Lescol XL 80mg` 與 `Lescol 40mg` 是兩回事）。
完整官方品名與健保代碼放在 `title`，要跟 HIS 對字時用。已停付的品項不列。

（出自 README 的『品項反查（代碼／商品名／學名 → 表一或表二）』節）

## 2026-09-01 條文分頁把品項併入藥理類別

**條文分頁把品項列在藥理類別裡面**（2026-09-01「健保規範條文分頁也要改」，
使用者選了「類別裡直接列品項，並拿掉下面兩份清單」）：同一頁把 165 個品項列兩次是純粹的損耗。
類別展開後是「學名 → 該學名的品項（帶表別）」，學名那一行保留條文的劑量錨點
（「高強度例：40 mg 以上」——品項檔沒有這個資訊）。開合狀態與計算機共用。
類別區塊本身可收合，但**給付標籤留在收合的那一行**：
「自費」藏起來等於引導醫師開一個病人要付錢的藥。

（出自 README 的『品項反查（代碼／商品名／學名 → 表一或表二）』節）

## 未標日期

### 側掛窄欄限寬靠右貼齊

**側掛窄欄在主視窗時限寬、靠右貼齊。** 網頁改不了主瀏覽器視窗的大小
（`resizeTo` 對一般分頁無效），所以解除置頂、側欄回到最大化的視窗時，沒有上限就會
攤成一片全寬版面——那既不是窄欄也不是工作台。

（出自 README 的『三種版面』節）

### 解除置頂時視窗夠寬就切回工作台

**解除置頂時，主視窗若寬到足以跑工作台（≥ 900px）就直接切回工作台。** 因為網頁
改不了自己所在視窗的大小——實測：一般分頁呼叫 `resizeTo(340,900)` 後 `innerWidth`
1266 → 1266 完全沒動，同一行在 `window.open` 開出來的視窗上則是 1266 → 326。
所以「側欄回到一個最大化的視窗」只能是「一條窄欄＋一大片空白」，那既不是側掛
也不是工作台。視窗本來就窄（Ctrl+Alt+D 貼齊的 340px）則維持側掛。

（出自 README 的『三種版面』節）

### 官方條文連結放在速判摘要之前

**每個主題最上方是官方條文 PDF 連結**，指向 [`健保條文/`](../健保條文/) 底下的檔案
（藥品給付規定的通則、第二節、第五節，加 PCSK9 事前審查申請表）。放在速判摘要之前是刻意的：
整理過的速查沒有機器可驗的權威來源，能反駁它的只有原始條文，所以原始條文要是第一眼
看得到的東西。`href` 由主文件的 `baseURI` 算成絕對路徑——側掛置頂時整棵窄欄在
Document PiP 的 `about:blank` 文件裡，相對路徑會解析到那邊去。
`chronic_care.json` 的 `docs[].file` 對不上實際檔案時**建置直接失敗**：
那種錯的表現是醫師在診間點下去說找不到檔案，而診間補不了檔。

（出自 README 的『健保規範條文（DM／HTN／LIPID）』節）

### 為什麼需要血脂計算機

**為什麼需要它**：LIPID 的給付判定有三個機械步驟特別容易錯，而三個都不需要臨床判斷——
用錯表（表一是主表，表二只適用公告明列「不適用表一」的健保代碼）、極高／非常高風險的
「組合」條件接錯（是「冠狀動脈疾病**合併**什麼」，不是單一條件）、兩張表的風險因子定義混用
（表一 6 項含代謝症候群、HDL-C 女性 < 50；表二 5 項含「或停經者」、HDL-C 男女同為 < 40）。

（出自 README 的『血脂計算機（給付試算）』節）

### 血脂計算機保留表二區塊

**兩張表一律都算**。表一是主表，表二在面板上退為次要區塊——但沒有移除，因為公告明列
「不適用表一」的那批代碼含 atorvastatin、rosuvastatin，常到不能不算。

（出自 README 的『血脂計算機（給付試算）』節）

### 表一藥物清單的收錄與排除

**表一用的是哪些藥**（階梯下方）：條文的「處方規定」欄只寫類別（statin、ezetimibe、
PCSK9 單株抗體、siRNA、ATP citrate lyase 抑制劑），這裡把台灣實際有的學名對進去，
並把**健保給付狀態與學名並排**——表一把 siRNA 與 ATP citrate lyase 抑制劑列為未達標時
可考慮的 non-statin 選項，但健保沒有收載（2.6 全文檢索命中 0），只列學名等於引導醫師
開一個病人要自費的藥。`covered` 少了或給付狀態沒寫，`build.py` 會讓建置失敗。
fenofibrate 與 gemfibrozil 刻意不收：它們走降三酸甘油酯那張表，混進來會讓人拿表一的
LDL-C 門檻去開 fibrate。

（出自 README 的『血脂計算機（給付試算）』節）

### 不適用表一成分只收到成分層級

**「不適用表一」的成分完整列在兩個地方**：LIPID 條文分頁（速判摘要下方）與血脂計算機的
表二區塊，兩邊同源於 `chronic_care.json` 的 `topics[lipid].tableTwoOnly`，不各存一份。
內容是 9 種成分共 116 個健保代碼（simvastatin 19、lovastatin 3、pravastatin 12、
fluvastatin 3、atorvastatin 35、rosuvastatin 25、pitavastatin 14、
pravastatin ＋ fenofibrate 複方 1、atorvastatin ＋ amlodipine 複方 4），
清單逐列讀自健保署官方第二節 `.docx` 的 2.6.1 對照表，再與同一份 PDF 交叉比對。
**刻意只收到成分層級**：116 列的代碼與品名變動頻繁，嵌進單檔就是製造一個會過期又看起來
權威的東西；成分層級足以回答「我開的這個要對哪張表」。`codeCount` 與各成分加總對不上時
`build.py` 會讓建置失敗——畫面上那句「限『不適用表一』的 N 個健保代碼」不能跟底下的清單自相矛盾。
同一位病人可能表一未達、表二卻符合（或反之），差別只在你要開的品項走哪一張表——
結論不同時面板會明講。判定邏輯是 `logic.js` 的純函式 `lipidCoverage()`，
單元測試在 `tests/logic.test.mjs`（逐級門檻、極高風險的組合條件、兩表風險因子定義的三處差異、
表二的「LDL 或 TC 兩選一」、fibrate 的兩列、以及沒填數值時不下判斷）。

（出自 README 的『血脂計算機（給付試算）』節）

### 表一表二品項數量不能憑印象假設

**不能假設「大多數走表一」**：就現行給付中的品項而言表二反而較多（116 vs 49），
逐學名看每一種 statin 都是表二多於表一。這一條是實際寫錯過的判斷——
把已停付的死碼算進去會得到「表一 255／表二 116」的相反印象，
而錯的方向會讓醫師少對代碼。`tests/test_lipid_products.py` 把它釘住了。

（出自 README 的『品項反查（代碼／商品名／學名 → 表一或表二）』節）

### 類別層級資訊留在條文分頁

**類別層級的資訊留在條文分頁**（`chronic_care.json` 的 `topics[lipid].drugs`）：
那一頁回答「表一叫我開什麼類別的藥」，計算機回答「我實際能開哪一個品項」。
給付狀態與學名並排是刻意的：siRNA 與 ATP citrate lyase 抑制劑被表一點名，
但健保沒收載，只列學名等於引導醫師去開一個病人要自費的藥；
計算機那邊用一行帶過（PCSK9 走 2.6.4 須事前審查、那兩類自費）。

（出自 README 的『品項反查（代碼／商品名／學名 → 表一或表二）』節）
