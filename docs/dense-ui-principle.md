# 版面密度原則：在有限的版面塞入最大量的資訊

> 使用者原話（2026-08-11，針對側掛窄欄的 header）：
>
> 「我希望這些按鈕只佔一列就好　門急診外科的按鈕不用這麼寬　緊縮跟文字一樣寬就好
> **這個介面的中心原則就是在有限的版面塞入最大量的資訊**」

這是產品原則，不是一次性的修正要求。**改動側掛窄欄（1c）與手機（1b）版面時，
以本檔為準；與其他設計參考（含 `.review/design-ref/` 的交付稿）衝突時，本檔優先。**

## 為什麼這條原則對這個產品特別重要

這支工具的使用情境是**看診中**：側掛窄欄貼在 HIS 旁邊，寬度只有 176〜600px，
醫師一邊問診一邊掃視。版面上每多一列 chrome（控制項、留白、看過就沒用的提示），
就少一列**診斷碼**——也就是少一個「不用打字、不用搜尋、直接點」的機會。
捲動一次的成本在門診是很高的，所以「省下 30px」不是美學問題，是動線問題。

## 原則

**版面預算優先給內容（診斷碼、主訴、部位），不給控制項與留白。**
任何佔用固定高度的東西都要能回答：它每一次看診都被用到嗎？沒有它會怎樣？

## 硬性邊界：不得為了塞而犧牲

以下四條**優先於密度**。壓縮到踩線就停手，改壓別的地方。

1. **手機觸控目標 ≥ 44px。** 那是手指的物理尺寸，不是風格選擇。
   `mobile.css` 的 44px（部位 pill、面板展開鈕、清單列小鈕、搜尋框、設定鈕）一律不准調小。
   側掛窄欄是滑鼠操作，不受這條約束，但仍不宜低於 20px 高。
2. **文字不可小到看不清。** 本專案的下限：主要內容（診斷碼、中文名）≥ 11px；
   次要 chrome（模式鈕、提示）≥ 10px。低於 10px 一律不准。
   手機搜尋框另有 16px 下限（低於 16px 會讓行動瀏覽器聚焦時自動放大整頁）。
3. **臨床安全的視覺分層不得被壓到看不出來。** 具體是三項：
   急診紅旗（`.chip--warn` 的警示色下緣）、不可申報的類目碼（`.chip.cat` 的虛線與
   `aria-disabled`）、附加碼標記（`.chip-tag` 與清單頂端的主診斷警示）。
   這三項的顏色、邊框、標記文字不因密度調整而弱化或移除。
4. **藏起可見文字時，可讀名稱必須有替代來源。** 只留 icon 的控制項一定要有能自我說明的
   `title`（且隨狀態更新），狀態另有 `aria-pressed` 之類的第二條線索。
   **砍文字是最後手段**：要先試過壓內距、壓字級、壓 letter-spacing，
   而且要在程式碼註解裡留下「為什麼非砍不可」的寬度算式（見 `dock.css` 的 media query）。

## 換到密度的手法（依「先做哪個」排序）

1. **控制列能合併就合併。** 一列 chrome 的固定成本是內容高度＋間距，通常 26〜30px。
   例：模式三鈕原本自己佔一行，與置頂／設定併成同一列，header 97px → 67px。
2. **控制項收成內容寬，不要等寬撐滿。** `flex: 1` 撐滿是預設值不是設計決定；
   低頻控制項（一次看診設定一次的模式切換）不需要大靶。多出來的寬度交給彈性 spacer。
3. **單行不換行的 UI 骨架收 `line-height`。** 全域 body 是 `line-height: 1.55`（給內文的），
   套在 `white-space: nowrap` 的按鈕與標題上時，那 0.55 完全是留白。
   1c 的部位鈕、部位標題、面板標題一律收到 1.2〜1.25。**會換行的內文不要動**——
   那裡的行距是可讀性。
4. **一次性提示要自己消失。** 「已開啟置頂小視窗，可拖到 HIS 旁邊」是操作說明，
   看過就沒用，卻在 176px 下佔兩行約 27px。成功類提示設逾時自動收掉；
   **失敗／未解決的提示相反，永遠留著**（它講的是使用者下一步該做什麼）。
5. **內距對齊到版面基準，不要一區一個數字。** 1c 的基準是 5〜6px；
   清單摘要列原本 8/10px，比鄰居鬆卻沒有分隔作用（分隔靠上緣線），收齊即省 6px。
6. **位置用百分比／`calc()`，不要寫死魔術數字。** 設定 popover 的 `top` 從 93px 改成 `100%`
   （貼著 `position: relative` 的 header 下緣）：header 少一列、或提示列讓 header 長高，
   都不必回頭改這個數字。寫死的數字每次改版都會失準一次，而失準的後果是
   popover 蓋住開它的那顆鈕、使用者關不掉。1b 早就是這個寫法。

## 刻意**沒有**做的事（附理由，避免日後被當成漏掉）

- **把「全部」鈕併進部位格線當第一格。**
  量過才知道沒有效益：176px 是兩欄，三種模式的部位數都是偶數（門診／外科 10、急診 8），
  併進去之後總格數變奇數，最後一格空著，**列數完全不變、省 0px**。
  565px 下才省得到一列（23px），但要付出「全部」被當成其中一個部位的語意代價
  （見 `dock-design-deviations.md`）。有效益的寬度換不到值得的代價，故不動。
  日後若部位數變成奇數，這筆帳要重算。
- **壓縮手機版面的幾何。** 1b 的高度幾乎全部由 44px 觸控目標決定，能動的只有
  header／部位列的內距（合計約 10px，佔 844px 螢幕的 1.2%），
  卻要冒動到 971 行手機 E2E 的風險。手機要提升密度應該從「一屏能放幾個碼」下手
  （內容區的列高與分組），不是從 chrome 的內距。
- **再壓搜尋框（28px）與「複製並貼入 HIS」（30px）。**
  這兩個是主要輸入與主要行動，各只有一份，壓下去換到的像素少、誤觸成本高。

## 怎麼驗證（改這塊之前先看這裡）

- `tests/test_e2e_dock.py::test_header_controls_share_one_row`
  ——五個控制項同列、模式鈕是文字寬、不溢出、文字不被裁切、header ≤ 72px。
- `tests/test_e2e_dock.py::test_pin_label_is_the_only_text_dropped_and_only_when_narrowest`
  ——176px 只有「置頂」兩個字被藏起（且 `title` 補上），模式鈕與「設定」的文字任何寬度都在；
  565px 文字必須回來。
- `tests/test_e2e_dock.py::test_pin_note_success_auto_dismisses_failure_stays`
  ——成功提示會自己消失、失敗提示不會。
- `tests/test_e2e_dock.py::test_no_horizontal_overflow`（日／夜 × 三模式）與
  `test_settings_popover_fits_and_switches_mode`（popover 不得蓋住開它的鈕）。

新的密度調整**一律要有對應的量測數字**（改前／改後、176 與 565 兩個寬度、日夜兩套主題），
不接受「看起來比較緊」。
