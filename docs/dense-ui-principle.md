# 版面密度原則：在有限的版面塞入最大量的資訊

> 使用者原話（2026-08-11，針對側掛窄欄的 header）：
>
> 「我希望這些按鈕只佔一列就好　門急診外科的按鈕不用這麼寬　緊縮跟文字一樣寬就好
> **這個介面的中心原則就是在有限的版面塞入最大量的資訊**」

這是產品原則，不是一次性的修正要求。**改動側掛窄欄（1c）與手機（1b）版面時，
以本檔為準；與其他設計參考（含 `.review/design-ref/` 的交付稿）衝突時，本檔優先。**

## 為什麼這條原則對這個產品特別重要

這支工具的使用情境是**看診中**：側掛窄欄貼在 HIS 旁邊，寬度只有 176〜600px，
醫師一邊問診一邊掃視。版面上每多一列 chrome（控制項、留白、看過就沒用的提示），
就少一列**診斷碼**——也就是少一個「不用打字、不用搜尋、直接點」的機會。
捲動一次的成本在門診是很高的，所以「省下 30px」不是美學問題，是動線問題。

## 原則

**版面預算優先給內容（診斷碼、主訴、部位），不給控制項與留白。**
任何佔用固定高度的東西都要能回答：它每一次看診都被用到嗎？沒有它會怎樣？

## 硬性邊界：不得為了塞而犧牲

以下四條**優先於密度**。壓縮到踩線就停手，改壓別的地方。

1. **手機觸控目標 ≥ 44px。** 那是手指的物理尺寸，不是風格選擇。
   `mobile.css` 的 44px（部位 pill、面板展開鈕、清單列小鈕、搜尋框、設定鈕）一律不准調小。
   側掛窄欄是滑鼠操作，不受這條約束，但仍不宜低於 20px 高。
2. **文字不可小到看不清。** 本專案的下限：主要內容（診斷碼、中文名）≥ 11px；
   次要 chrome（模式鈕、提示）≥ 10px。低於 10px 一律不准。
   手機搜尋框另有 16px 下限（低於 16px 會讓行動瀏覽器聚焦時自動放大整頁）。
3. **臨床安全的視覺分層不得被壓到看不出來。** 具體是三項：
   急診紅旗（`.chip--warn` 的警示色下緣）、不可申報的類目碼（`.chip.cat` 的虛線與
   `aria-disabled`）、附加碼標記（`.chip-tag` 與清單頂端的主診斷警示）。
   這三項的顏色、邊框、標記文字不因密度調整而弱化或移除。
4. **藏起可見文字時，可讀名稱必須有替代來源。** 只留 icon 的控制項一定要有能自我說明的
   `title`（且隨狀態更新），狀態另有 `aria-pressed` 之類的第二條線索。
   **砍文字是最後手段**：要先試過壓內距、壓字級、壓 letter-spacing，
   而且要在程式碼註解裡留下「為什麼非砍不可」的寬度算式（見 `dock.css` 的 media query）。

## 換到密度的手法（依「先做哪個」排序）

1. **控制列能合併就合併。** 一列 chrome 的固定成本是內容高度＋間距，通常 26〜30px。
   例：模式三鈕原本自己佔一行，與置頂／設定併成同一列，header 97px → 67px。
2. **控制項收成內容寬，不要等寬撐滿。** `flex: 1` 撐滿是預設值不是設計決定；
   低頻控制項（一次看診設定一次的模式切換）不需要大靶。多出來的寬度交給彈性 spacer。
3. **單行不換行的 UI 骨架收 `line-height`。** 全域 body 是 `line-height: 1.55`（給內文的），
   套在 `white-space: nowrap` 的按鈕與標題上時，那 0.55 完全是留白。
   1c 的部位鈕、部位標題、面板標題一律收到 1.2〜1.25。**會換行的內文不要動**——
   那裡的行距是可讀性。
4. **一次性提示要自己消失。** 「已開啟置頂小視窗，可拖到 HIS 旁邊」是操作說明，
   看過就沒用，卻在 176px 下佔兩行約 27px。成功類提示設逾時自動收掉；
   **失敗／未解決的提示相反，永遠留著**（它講的是使用者下一步該做什麼）。
5. **內距對齊到版面基準，不要一區一個數字。** 1c 的基準是 5〜6px；
   清單摘要列原本 8/10px，比鄰居鬆卻沒有分隔作用（分隔靠上緣線），收齊即省 6px。
6. **位置用百分比／`calc()`，不要寫死魔術數字。** 設定 popover 的 `top` 從 93px 改成 `100%`
   （貼著 `position: relative` 的 header 下緣）：header 少一列、或提示列讓 header 長高，
   都不必回頭改這個數字。寫死的數字每次改版都會失準一次，而失準的後果是
   popover 蓋住開它的那顆鈕、使用者關不掉。1b 早就是這個寫法。

模式鈕從等寬撐滿（每顆 53〜54px、整列 164px）收成文字寬（每顆 28〜29px、整列 89.2px）。

## 刻意**花掉**密度的一筆：慢病速查「一條一行」（2026-08-26）

使用者原話：「出現『；』分號這種　看起來就是第二個句子或是另一個適用條例　
這種是否換行或分段會比較好閱讀」。條文改成依句號＋分號斷段、掛項目符號與懸掛縮排
（`.chronic-seg`）。這是**用版面換可讀性**，方向與本檔相反，所以要有數字。

同一天的第二輪：使用者再指出「Fibrate：第一列黏在抬頭上、第二列變孤兒」，
於是主文的短標提成獨立的**抬頭行**（`.chronic-seg.is-head`），底下條件全部平行掛——
多一列的成本就是下表兩個數字的差（收合 2556→2597）。

Playwright 量測 `#chronic-body` 的 `scrollHeight`，LIPID 主題（21 條）：

| 版面 | 收合（預設狀態） | 全部補充攤開 |
| --- | --- | --- |
| 1c 176px | 2544 → 2597（**+53，+2.1%**） | 9090 → 10089（+999，+11.0%） |
| 1c 565px | 1306 → 1411（+105，+8.0%） | 3710 → 4215（+505，+13.6%） |
| 1b 手機 390px | 2507 → 2567（+60，+2.4%） | 6454 → 6900（+446，+6.9%） |
| 1a 桌機 1280px | 1467 → 1590（+123，+8.4%） | 4039 → 4567（+528，+13.1%） |

**為什麼 176px 收得下**：那 14 條含分號的主文本來就會折行，在分號處斷開多半只是把
折行位置換個地方；抬頭行也只發生在 6 條有短標的條目上。真正的成本落在「補充攤開」
——但那是使用者主動點開、要逐條讀的狀態，正是可讀性該優先於密度的地方。

懸掛縮排 `.8em`（176px 下約 8.8px）也是刻意的最小值：夠讓續行縮進去看得出來，
又不至於在最窄欄吃掉一個字的寬度。**單段的條目不掛符號也不縮排**，所以 51/65 條
完全維持原樣。三套版面 × 日夜主題皆無水平溢出（`test_chronic_panel_never_overflows_at_176`）。

## 第二筆：對回官方原文重寫，版面又翻了一倍（2026-08-26）

使用者要求「重讀官方文件後用類似方式重寫」。64 條逐條對回官方原文之後，把原本只躺在
「補充」、但實際屬於**能不能開**的門檻拉上主文（例：SGLT2i 心衰竭補上 LVEF 41–49% 路徑、
PCSK9 續用補上 HoFH 那組不同的數字、表二補上危險因子分級）。

同一組量法，LIPID 主題（21 條）從**改版前的原始基準**到現在：

| 版面 | 收合（預設狀態） | 全部補充攤開 |
| --- | --- | --- |
| 1c 176px | 2544 → 5070（**+99%**） | 9090 → 13000（+43%） |
| 1c 565px | 1306 → 2729（+109%） | 3710 → 5664（+53%） |
| 1b 手機 390px | 2507 → 4364（+74%） | 6454 → 8942（+39%） |
| 1a 桌機 1280px | 1467 → 3158（+115%） | 4039 → 6283（+56%） |

**這一倍幾乎全部是內容，不是排版。** 純排版（分號斷行＋抬頭行）在 176px 收合狀態只佔
+2.1%（2544→2597，見上一節）；其餘是主文多載了門檻條件。

**為什麼判斷值得**：這個面板存在的理由就是回答「能不能開」。門檻藏在收合的補充裡，
等於醫師掃主文會拿到不完整的判準——LVEF 45% 的病人原本會被主文誤判成不給付。
把答案放在會被看到的地方，比省版面重要。

**評估過「回收版面」，結論是不划算**：逐條看完 64 項，真正可砍的只有 5 段
（「換句話重講」與「指向隔壁條目」，例如 #13 與 #15 互相重複的那句、
「指引各表的 office BP 一律指標準化診間血壓」這種讀指引的方法）。已經砍掉，
但那只值約 3% 的高度，而每多砍一段就多一分誤刪門檻的風險。**其餘保留。**

**改用不花版面的方式解決捲動痛點**：分段標題（能不能開／怎麼開／別踩雷／不給付／治療目標）
改成 `position: sticky`。捲長一格沒少，但「捲到一半不知道自己在哪一段」消失了——
sticky 重複利用的是本來就存在的那一列，量測前後 `scrollHeight` 完全相同。
醫師開這個面板時心裡有個特定問題，標題常駐才對得上那個問題。

實作兩個細節（都實測過）：sticky 元素**必須給不透明背景**，否則捲過去會有兩層字疊在一起；
「別踩雷」「不給付」兩段有左邊界線與內距，標題要 `margin-left: -8px; padding-left: 8px`
把背景拉滿那塊內距，但**保留那 2px 邊界線**——它是該段的身分標記。

三套版面 × 日夜主題仍無水平溢出。

## 第三筆：入口三鈕併成一顆、CCr 搬進同一排（2026-09-01）

使用者要求「DM／HTN／LIPID 整合成『健保規範條文』一顆」、「血脂改叫血脂計算機、
CCr 放到它右邊」。做完之後那一排是 **健保規範條文｜血脂計算機｜CCr**。

量測條件同上（Playwright，1c 側掛窄欄，176／565px × 日夜；日夜同值故只列一組）。

| 量的東西 | 176px 改前 → 改後 | 565px 改前 → 改後 |
| --- | --- | --- |
| `.dock-head`（固定 chrome） | 92 → **92**（不變） | 67 → **67**（不變） |
| `#chronic-switch`（在捲動區） | 33 → **58**（+25，折成兩列） | 33 → **33**（不變） |
| `.dock-scroll` clientHeight | 686 → 686 | 734 → 734 |
| `.dock-tools` 需要的寬度／可用 | 249.3 → 218.1／163 | 249.3 → 218.1／327 |

**這一筆是淨支出，不是節省。** 我原本在註解裡寫「CCr 搬走，header 的寬度帳就鬆開了」，
量了才發現不成立：`.dock-tools` 在 176px 需要 249.3px、可用只有 163，本來就折成兩列；
搬掉 CCr 後 218.1 仍然折，`.dock-head` 一樣是 92px。真正省到的只有
**231–262px 這一段 dock 寬度**（在這區間內原本折兩列、現在一列），
而使用者實際用的 340／565px 兩個寬度本來就不折——**在他的機器上是零收益**。

代價則是實的：176px 下三顆放不進一列（79.3 ＋ 70.1 ＋ 28.2 ＝ 178 ＞ 163），
`.chronic-switch` 開 `flex-wrap` 折成兩列，那一排 33→58px。它在捲動區裡，
永久成本仍是 0（往下選碼時就捲走了），但**第一屏少了 25px 的代碼**。

**為什麼還是做**：這是使用者指定的整併，不是密度優化——把它記在這裡是為了防止日後
有人翻到那幾行註解，以為「搬 CCr」是一個省版面的手法而照抄。真正的收益是動線
（兩個計算機放一起只要記一個位置），密度上它要付 25px。

另外，同一輪抓到一個**既有**的觸控門檻破口：`#lipid-btn` 帶著 `.seg-btn--sm`
（那是給 176px 的 22px／10px），手機版沒有蓋掉它，實測只有 22px 高、10px 字，
遠低於 44px 硬性邊界。它從 2026-08-26 加入時就是壞的，因為當時的手機 E2E 只量
`.chronic-btn`。現在 `mobile.css` 補了規則，測試也改成逐顆量這一排的三個 id。

## 刻意**沒有**做的事（附理由，避免日後被當成漏掉）

- **把「全部」鈕併進部位格線當第一格。**
  量過才知道沒有效益：176px 是兩欄，三種模式的部位數都是偶數（門診／外科 10、急診 8），
  併進去之後總格數變奇數，最後一格空著，**列數完全不變、省 0px**。
  565px 下才省得到一列（23px），但要付出「全部」被當成其中一個部位的語意代價
  （見 `dock-design-deviations.md`）。有效益的寬度換不到值得的代價，故不動。
  日後若部位數變成奇數，這筆帳要重算。
- **壓縮手機版面的幾何。** 1b 的高度幾乎全部由 44px 觸控目標決定，能動的只有
  header／部位列的內距（合計約 10px，佔 844px 螢幕的 1.2%），
  卻要冒動到 971 行手機 E2E 的風險。手機要提升密度應該從「一屏能放幾個碼」下手
  （內容區的列高與分組），不是從 chrome 的內距。
- **再壓搜尋框（28px）與「複製並貼入 HIS」（30px）。**
  這兩個是主要輸入與主要行動，各只有一份，壓下去換到的像素少、誤觸成本高。

## 怎麼驗證（改這塊之前先看這裡）

- `tests/test_e2e_dock.py::test_header_controls_share_one_row`
  ——五個控制項同列、模式鈕是文字寬、不溢出、文字不被裁切、header ≤ 72px。
- `tests/test_e2e_dock.py::test_only_pin_and_expand_labels_are_dropped_and_only_when_narrowest`
  ——176px 只有「置頂」與「展開」的文字被藏起（`aria-label` 與 `title` 補上），
  模式鈕與「設定」的文字任何寬度都在；565px 文字必須回來。
- `tests/test_e2e_dock.py::test_pin_note_success_auto_dismisses_failure_stays`
  ——成功提示會自己消失、失敗提示不會。
- `tests/test_e2e_dock.py::test_no_horizontal_overflow`（日／夜 × 三模式）與
  `test_settings_popover_fits_and_switches_mode`（popover 不得蓋住開它的鈕）。

新的密度調整**一律要有對應的量測數字**（改前／改後、176 與 565 兩個寬度、日夜兩套主題），
不接受「看起來比較緊」。
